# ERPNext v16 解耦重建长期计划

## 目标与边界
以 ERPNext 的成熟业务经验作为研究输入，按照 Platform 的资源、对象、动作、关系、状态、权限和产品包契约重新设计一套可独立安装、可组合、可升级的企业应用体系。不是移植 ERPNext，也不是把每个 DocType 变成 YAML。用户可只买库存，不必装会计；买卖、制造、会计在组合安装后通过明确的业务契约协作。遵守 Platform 八个承重决定和本库四类包依赖规则。业务规则留在包，通用能力缺口进入 Platform/inner-box。

固定来源：
- ERPNext：本地 ../Frappe/erpnext，version-16，8e10a348daaa93853de8c36dc55ec789a440c219，GPL-3.0。
- Frappe Framework：../Frappe/frappe，version-16，49789a1711d4dde2be9c6888efe35651465f4b64，MIT；只追 ERPNext 使用的框架机制，另行登记是否需要平台通用能力。
- Platform：本轮基线 9a2177b5b。执行每波时重新记录完整 commit 及 platform.lock。
- 全量范围以 inventory.md、source-index.tsv、doctype-index.tsv、module-edges.tsv 为准。静态普查已完成，源码逐项研究未完成。版本升级另做增量审阅。
- 本库原有 intake.md、sources.md、format.md、testing.md、release.md 为交付规范。GPL/AGPL 参考只做 redesign，不复制代码、定义、文案、UI 或独创实现；如确有转换需求，另设原许可仓库，商业交付前法律评审。

## 研究方法与证据标准

每模块至少走一遍实际用户主线，读文档、DocType/工作区元数据、控制器、JS 交互、报表、测试，再追到 hooks、共用控制器、权限、后台任务、补丁和框架机制。每个核心业务场景用至少两种独立产品设计对照（参考 sources.md 的推荐；尚未完成的对照不能声称已经研究）。源码索引状态为 indexed / partially-reviewed / reviewed / out-of-scope（需写原因），模块验收状态为 discovered / researched / designed / implemented / verified / released。两类状态不互相替代。

每个设计写：
1. 用户角色、每日工作、业务意图、输入/结果、完整正反流程；不要把现有 UI 菜单当业务边界。
2. 证据：来源固定 commit、文件路径、符号/行区间、测试名称、实际观察；只记录事实与独立抽象。
3. 领域模型：对象、关系、共享属性、值类型、接口、独立动作、状态机、业务字典、派生值、权限范围及导航。
4. 不变量：唯一性、守恒、金额精度、重复提交、并发、冲正、审计、重放与升级。
5. 解耦：谁拥有事实，谁消费事实；契约版本、输入输出、权限、失败和重试、组合安装/卸载行为。
6. 能力对照：当前平台支持 / 待验证 / 已证实缺口 / 本期不做，缺口必须链接 inner-box ID。不能在包中绕过统一写入、授权或版本边界。
7. 可运行验收：pkg try、pkg check、跨包组合、角色正反例、浏览器主线、重启恢复与升级；未跑就标未跑。

## 包边界（候选设计，不代表已发布目录）

| 来源模块 | 目标包/平台落点 | 处理原则 |
|---|---|---|
| Setup | 已有 geo、party、uom；候选 item-master；平台企业组织、币种与日历 | 共用主数据只维护一份；法人与账套语义另查 |
| Stock | item-master、inventory；可选仓储扩展 | 商品身份与库存事实分离；库存移动和余额同一权威 |
| Buying | purchasing | 请购、询价、采购订单、到货确认、供应商评估 |
| Selling | sales | 报价、订单、交付需求、退货；不重复 CRM 线索 |
| Accounts | accounting，必要时税务本地化扩展 | 总账、应收应付、收付款、成本、期结；独立会计权威 |
| Manufacturing | manufacturing | BOM、工艺、工单、领料需求、完工、计划；库存事实不在制造包重复维护 |
| Subcontracting | subcontracting 或 manufacturing 扩展（待研究） | 委外用料、供应商交付、耗用和结算；先确认能否独立安装 |
| Quality Management | quality | 检验规范、抽样、质检判定、不合格与纠正措施；检验结论供其他包消费 |
| Assets | 现有 assets；财务资产能力由 accounting 协作 | 实物与折旧分离，不新造资产包 |
| Maintenance | 现有 assets 扩展或独立 maintenance（待研究） | 保养计划、故障、维修与备件 |
| Projects | 现有 projects | 项目与工时、费用归集，增量补足 |
| CRM | 现有 crm | 只补缺失业务意图，不重建 |
| Support | 现有 helpdesk | 支持工单与 SLA，核对合同和保修 |
| Utilities | 通用平台能力或对应领域 | 不建杂物包 |
| Portal | 平台外部用户入口 / 各业务包页面 | 不另造门户运行时 |
| Regional | 税务与会计本地化扩展 | 按司法辖区独立研究、法律核对；不把一国规则写死到核心 |
| ERPNext Integrations | 能力契约、连接器 | 不绑定具体供应商，凭据只保存引用 |
| Communication | 平台通知、工作活动或能力包 | 不重复消息基础设施 |
| Telephony | 已有 call、phone | 核对契约与使用方，不新建 |
| Bulk Transaction | 平台批量动作、导入与任务运行时 | 批处理是通用能力；业务校验仍走动作 |
| EDI | 候选 EDI 能力包及供应商实现 | 版本化交换文档、幂等、失败回执；先查实际协议 |
| 跨模块目录与根文件 | controllers、hooks、patches、public、tests、templates、www 等 | 全量索引，逐波追踪；框架通用机制进入缺口，不移植代码 |

## 跨包解耦约束
- 既有 party/geo/uom 作为共享名词；先研究 crm.product 的身份及数据迁移，再决定 item-master 的最小公共身份，不能直接新增第二套商品主数据并称完成。
- 应用包不能直接依赖另一个应用包。现有允许的依赖是主数据与能力契约。库存、采购、销售、制造、会计之间以稳定业务事实与契约连接；是否能由现有包级契约及执行路径表达必须实测，不能先假设支持。
- 契约候选如库存预留/释放、移动过账、发货/收货确认、成本事实/会计过账请求、质检判定；这些是意图，不是现有 API。契约包含关联 ID、版本、幂等键、状态、数据范围、拒绝原因和重试语义。
- 跨权威原子性不可假设：一个权威内完成原子业务变更；跨包用受支持的提交/事件/补偿与对账机制。对必须同事务的业务，重新审定权威边界，不用异步事件掩盖不变量。
- 对每个组合验证：独立安装、缺依赖拒绝、升级兼容、权限不扩大、停用/卸载不丢其他包数据。

## 交付与市场
每个正式包按现有模板建立 packages/<id>/：package.yaml、DESIGN.md、README、CHANGELOG、LICENSE、对象/动作/页面/流程/角色、locales/zh-CN.yaml、try.yaml、锁文件。DESIGN.md 先于运行时 YAML。每包定位一句话，默认工作视图服务角色；不得复制来源界面。
catalog.json 是不可变发布制品的索引，不是规划表。计划中的包留在本文件，不伪造 URL、SHA-256 或已发布版本。使用锁定 pkg 构建与校验、node scripts/packages.mjs catalog 生成目录、catalog --check 校验；遵守真实 Release 发布和升级规则。
封面按 docs/format.md：packages/<id>/assets/cover.avif，720×540（4:3），真实业务主题、无来源商标、缩略图仍可辨识，核对尺寸/大小/文件头及真实卡片。封面单独更新不升运行时版本。每包发布前必须具备封面（本计划新增要求）。先确定实际包名和业务定位再画，不给未设计完的包制作假成品。
