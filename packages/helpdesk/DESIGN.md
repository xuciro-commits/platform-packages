# Helpdesk（售后与客户支持中心）设计稿

## 一句话

客服的一天从“快超时的工单”开始。每张工单按优先级背负首次响应与最终解决双时限，未指派的工单自动均衡落到人；
打开售后中心先看到今天该救火的队列，而不是翻找杂乱的邮件。

## 从成熟产品里看到的套路

我们横向对照了 **Frappe Helpdesk**、**Zammad** 与 **OCA Helpdesk**（`helpdesk_mgmt` + `helpdesk_mgmt_sla`），提炼出售后支持的八个核心套路：

| 套路 | 在哪里看到 | 我们怎样做 |
|---|---|---|
| 生命周期与处理阶段分离 | 针对 Frappe Helpdesk / Zammad 的设计债重构 | Frappe 与 Zammad 把 `Open`、`Waiting`、`Resolved`、`Closed` 混在同一个状态字段里，容易误点关闭跳过解决说明。我们把生命周期交给平台状态与动作（`open → resolved → closed` + `reopen`），把进行中的处理阶段（待受理、处理中、等客户、已升级）做成看板列 |
| 双 SLA（首次响应 + 最终解决） | Frappe Helpdesk、Zammad、OCA SLA | 每张工单自带 `responseby` / `resolveby` 与对应 SLA 状态（待达标、已达标、已超时）；到期未达标自动标记超时并通知负责人 |
| 按队列分流与负载均衡派单 | Frappe Helpdesk、Zammad、OCA | 工单归属客服队列（技术支持、账务咨询、实施交付、二线升级）；未指定负责人的新工单按一线客服当前在手开放工单数自动均衡分配 |
| 对外回复与内部协作分离 | Frappe Helpdesk、Zammad | 回复对象 `helpdesk.reply` 区分「对外回复」与「内部备注」；通过工单上的「回复客户」动作一步写入回复，对外回复自动推动首次响应 SLA 达标并将阶段推进至「处理中」 |
| 结构化升级（Escalation） | Zammad | 升级不是随手改个标签，而是独立动作：必填升级原因，可同时转入二线队列与新负责人，看板直接进「已升级」列 |
| 结构化解决与知识沉淀 | Frappe Helpdesk、Zammad | 解决工单必须选解决根因并写明方案，可选关联知识库文章；知识库有独立草稿/发布/归档生命周期，常用回复模板沉淀高频话术 |
| 客户与联系人维度的历史聚合 | Frappe Helpdesk、Zammad | 客户档案自动汇总当前开放工单数与累计工单数，客服一眼识别高风险大客户 |
| 关闭与满意度闭环（CSAT） | Frappe Helpdesk、Odoo Helpdesk | 工单解决后可记录 1–5 分满意度与客户反馈再关闭，若客户不满意可走重开动作并说明原因 |

## 落到平台的六个词

| 平台词 | 产品问题 | Helpdesk 的答案 |
|---|---|---|
| 状态（`states` + `from`） | 生命有几段？哪些只能走动作？ | 工单 `open / resolved / closed`；知识文章 `draft / published / archived` |
| 字典（带 `records` 的类型） | 哪些配置由客服主管维护？ | 处理阶段（九色看板列）、优先级（响应/解决目标小时与九色）、客服队列、问题分类、来源渠道、解决根因 |
| 动作（带 `inputs` 与事务） | 哪一步必须一次做完、问清什么？ | 回复客户（同时建回复记录并达标首次响应）、升级（必填原因并转派）、解决（必填根因与方案）、关闭（记录 CSAT）、重开（必填原因） |
| 派生（`from`、`formula`） | 哪些数不该让人手填？ | 目标响应/解决小时从优先级带出；工单回复数、客户开放工单数/累计工单数、队列开放工单数自动汇总 |
| 角色与范围（`access`、`scope`） | 谁看谁的？ | 一线客服 `agent` 看本单元工单、读写知识库与模板、字典只读；客服主管 `supervisor` 看全量、可归档并独占设置页 |
| 注意力（`view.inbox`、`lanes`、flow、仪表盘） | 什么时候推到谁面前？ | 解决截止时间进负责人收件箱；响应/解决 SLA 超时发通知；看板按处理阶段分列；仪表盘盯超时、升级与根因占比 |

## 对象

| 对象 | 是什么 | 关键字段 |
|---|---|---|
| 工单 `helpdesk.ticket` | 一次客户求助或故障报修 | 主题、客户、联系人、问题描述、处理阶段、优先级、队列、分类、渠道、负责人、首次响应截止与 SLA、解决截止与 SLA、目标响应/解决小时、回复数、升级原因、解决根因、解决方案、关联知识文章、解决日、CSAT 评分与反馈 |
| 工单回复 `helpdesk.reply` | 工单下的一条对外回复或内部备注 | 工单、可见性（对外回复 / 内部备注）、内容、作者 |
| 知识文章 `helpdesk.article` | 可复用的排障指南与常见问题 | 标题、分类、摘要、正文、作者、状态（草稿 / 已发布 / 已归档） |
| 常用回复 `helpdesk.cannedreply` | 高频问题的标准回复模板 | 标题、分类、正文、启用 |
| 客户 `helpdesk.customer` | 接受售后服务的客户组织 | 名称、服务等级（标准 / 高级 / 专属）、域名、专属负责人、开放工单数、累计工单数 |
| 联系人 `helpdesk.contact` | 提交工单的具体联系人 | 姓名、所属客户、邮箱、手机、职务 |

字典（全部收纳在主管专属的 `layout: settings` 设置页，带参考记录）：处理阶段 `helpdesk.stage`、优先级 `helpdesk.priority`、客服队列 `helpdesk.queue`、问题分类 `helpdesk.category`、来源渠道 `helpdesk.channel`、解决根因 `helpdesk.resolution`。

## 角色与可见性

| 角色 | 工单与回复 | 客户、联系人、知识库、常用回复 | 字典与设置页 |
|---|---|---|---|
| 一线客服 `agent` | 读本单元，建、改；不能归档 | 读全部，建、改 | 只读（看不到设置菜单） |
| 客服主管 `supervisor` | 读全部，建、改、归档 | 读全部，建、改、归档 | 增改与归档 |

## 自动化

| 流程 | 触发 | 效果 |
|---|---|---|
| 自动均衡派单 `helpdeskassign` | 新工单无负责人且处于 `new` 阶段 | 按一线客服 `agent` 在手开放工单数最少自动指派 |
| 首次响应达标 `helpdeskresponded` | 工单离开 `new` 阶段且 `responsesla = due` | 自动标为 `met` |
| 首次响应超时 `helpdeskresponsesla` | 工单进入 `open` | 等待 `responseby`，仍为 `due` 则标 `missed` 并通知负责人 |
| 解决超时 `helpdeskresolutionsla` | 工单进入 `open` | 等待 `resolveby`，仍为 `due` 则标 `missed` 并通知负责人 |

## 受平台限制的取舍与发现的平台缺口

1. **按优先级动态计算截止时间**：平台当前 `default: now+4h` 只支持静态时长偏移，还不能按所选优先级字典的 `responsehours` / `resolvehours` 动态计算 `responseby` / `resolveby`（例如紧急 1h、普通 4h）。本版默认 `responseby = now+4h`、`resolveby = now+24h`，同时在工单上通过 `from: priority.*` 带出目标小时数供客服核对。
2. **等待客户时暂停 SLA 计时**：Zammad 和 OCA 支持进入 `waiting` 阶段时暂停 SLA 钟表；平台当前 `waitUntil` 是单次时间点等待，不支持暂停/重算计时器。本版记录进入 `waiting` 阶段供人工辨别，暂停计时留作平台 SLA 引擎增强项。
3. **工作日历（Business Hours）**：平台暂无工作时间段日历，SLA 按自然小时计算。
4. **动作中无法写入当前时间戳**：受限于流程与动作表达式对时间戳字段的支持，暂用 `today()` 记录解决日期 `resolvedon`，首次响应记为达标状态 `met` 而非精确秒级时刻。
5. **跨包软联动（CRM ↔ Helpdesk）**：当前保持 `helpdesk` 独立可装，自带轻量客户与联系人；后续平台支持可选软依赖或共享 `party` 基础包后，可与 CRM 共用客户与联系人。

## 验收主线

在空租户安装 `helpdesk`：主管配置 `agent` 与 `supervisor` 角色；新建客户与联系人；创建未指派工单验证自动均衡派单与优先级目标小时带出；执行「回复客户」一步写入对外回复并使首次响应 SLA 达标；测试升级工单至二线队列；创建并发布一篇知识文章；执行「解决工单」关联知识文章并填写解决根因与方案，验证解决 SLA 达标；执行「关闭工单」写入 5 星 CSAT；验证客户开放/累计工单聚合数准确；再测试重开流转。
